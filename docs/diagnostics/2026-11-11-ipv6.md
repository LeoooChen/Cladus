# Codex login and IPv6 investigation — 2026-11-11

This records the initial investigation. See the [subsequent connection fallback
work](2026-11-11-fallback.md) for updated upstream observations, implementation,
validation and the live Magpie routing correction.

All times refer to Asia/Shanghai. No application was restarted, no system proxy
or DNS settings were changed, and no Clash node selection was changed by this
investigation. Network checks used independent unauthenticated requests.

## Findings

- Installed Cladus: 0.1.3, engaged, upstream SOCKS5 `127.0.0.1:7897`.
- The `chatgpt.exe` rule matches the desktop app. Its `codex.exe` children inherit
  the rule. Both TCP and UDP are enabled. Clash TUN is disabled.
- System DNS returns public IPv4 and IPv6 addresses for `chatgpt.com`. The IPv4
  answers match a separate DNS-over-HTTPS lookup through the proxy.
- An ordinary request intercepted by Cladus chooses IPv6 and fails during TLS.
  The same request constrained to IPv4 receives HTTP 200. Explicit SOCKS5 with
  proxy-side hostname resolution also receives HTTP 200.
- Bypassing Cladus and giving Clash the IPv6 address directly reproduces the
  failure. Independent Python TLS and Windows curl/Schannel clients agree.
- The actual Clash core reports Mihomo v1.19.33 and routes these requests through
  `HK Relay`, selected node `Hong Kong to Dubai`.

## Confirmed Cladus defect and correction

`relay::relay` discarded errors from `copy_bidirectional_with_sizes` using
`unwrap_or_default`. A reset after a successful SOCKS5 reply therefore became
`Ok((0, 0))`. The engine never incremented `relay.failed` or logged the failure.

The correction returns `RelayError::Transfer` with the original I/O error. The
existing engine error handling then increments the failure count and includes
the target, proxy and error in its warning. A regression test uses a real local
SOCKS5 peer that acknowledges CONNECT, reads tunnel data, and resets the socket.
The original implementation fails the test with `Ok((0, 0))`.

Clean TCP EOF alone is not an I/O error: an application protocol such as TLS can
consider it premature while a transport-only relay cannot. This correction must
not be represented as repairing the observed upstream TLS EOF or Codex login.

### Verification of the source correction

- Regression test with the original implementation: failed, reporting
  `reset was hidden: Ok((0, 0))`.
- Corrected workspace: 132 tests passed; the existing opt-in live-network test
  remained ignored. This includes SOCKS5 IPv6 serialization, normal bidirectional
  relay and half-close, DNS forwarding, and the new post-handshake reset test.
- Clippy with warnings denied, formatting, dependency-layer checks and diff
  whitespace checks passed. No dependency version was changed; the existing
  `socket2` crate is also used as an engine test dependency to generate TCP RST.
- Service/installer/WinDivert system tests were not run against the active
  installation, and the installed binary was not replaced.
