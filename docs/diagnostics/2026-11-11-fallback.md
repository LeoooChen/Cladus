# IPv6 fallback and AgentRouter routing — 2026-11-11

This follows the [initial investigation](2026-11-11-ipv6.md). The user subsequently
requested connection fallback, rather than DNS filtering. The abandoned domain
filtering changes were removed; no DNS filtering configuration was applied.

## Implementation in 0.1.4

The Windows TCP handoff now carries the original destination policy to the relay.
For IPv6 TCP port 443, the relay buffers at most 64 KiB of the first ClientHello,
waiting at most one second to recognize it. The original IPv6 tunnel is attempted
first. EOF, reset, connect failure or a three-second first-response timeout can
trigger fallback, but only when the ClientHello is complete and contains a usable
SNI name without early-data or ECH extensions.

Fresh A and AAAA queries go to `dns.upstream` over the same SOCKS5 proxy as this
connection, with a five-second DNS deadline. The original IPv6 address must be in
the verified hostname's AAAA answers. CNAME chains are followed; unrelated answer
records are not accepted. At most two allowed IPv4 addresses are tried, with a
twelve-second total fallback-stage deadline. Each alternate is checked against
the original connection's current destination policy.

Only ClientHello can be replayed. After receiving any server byte, including a
TLS alert, the relay commits to that tunnel and never retries it. Certificate and
TLS validation remain in the client. HTTP POST bodies, established TLS sessions
and streaming responses are never replayed by Cladus. Non-TLS traffic, non-443
ports, unverified SNI, ECH and 0-RTT keep the ordinary relay path.

`tcp_ipv6_fallback` defaults to true for existing and new configurations; Settings
has an immediate, reversible toggle. DNS answers, system IPv6 configuration and
healthy IPv6 paths are not changed. A warning preserves the original IPv6 error.
`relay.ipv4_fallback_attempted`, `selected` and `failed` counters describe the
fallback stage; selected means a first server byte arrived, not that an entire
application session succeeded.

### Isolated live acceptance

No WinDivert handle, service restart or system DNS change is used by
`apps/cladus-engine/examples/ipv6_fallback_probe.rs`. It connects a test-owned curl
process to a local listener and uses the production relay library.

During the later live check, the real upstream IPv6 path was working: ChatGPT
returned HTTP 200, with zero fallback attempts. This supersedes the earlier
observation that the upstream IPv6 path was failing; do not describe it as a
permanent current failure or attribute its recovery to this code.

A test-owned SOCKS shim then simulated success followed by EOF only for the
IPv6 attempt, while forwarding DNS and IPv4 to the real Clash listener. The
production fallback recorded the original EOF, verified DNS, connected to
`104.18.32.47:443` and returned HTTP 200 in about 0.71 seconds. Counters were
attempted=1, selected=1, failed=0. TLS verification was enabled.

Reproduce without touching the active installation:

```powershell
cargo run --locked -p cladus-engine --example ipv6_fallback_probe -- `
  --proxy 127.0.0.1:7897 --ipv6 2606:4700:4408::ac40:9bd1 `
  --host chatgpt.com --simulate-ipv6-eof
```

Use a current AAAA address for the hostname; stale or unrelated IPv6 addresses
are deliberately rejected.

## AgentRouter 502

The reported `192.168.1.2 -> 8.214.160.125:443` connection is IPv4, so it is not
an IPv6 fallback error. The request route in Codex configuration points to
`http://127.0.0.1:3425/v1`, whose listener belongs to
`D:\Program Files\magpie\magpie.exe`. Magpie is independently launched and was
not assigned a Cladus proxy rule; receiving a loopback request from ChatGPT does
not give it ChatGPT's process ancestry. Some observed Magpie connections already
used Clash explicitly, so the rule omission alone does not prove the cause of
every reset.

A path-scoped `magpie.exe` rule (`rule-magpie-api`) was added through Cladus's
authenticated service IPC, using the existing ChatGPT proxy group 0 and both
protocols. The service confirmed the running process was assigned to it. The
service saved its ordinary configuration backup. No process was restarted, no
existing request was replayed, and no Magpie, Clash or ChatGPT configuration was
modified. This closes the coverage gap for subsequent non-loopback connections.

Remote resets or failures after a stream has begun still require recovery at the
request/provider layer. A transparent encrypted TCP relay cannot safely resume
or replay a partially executed POST. No claim is made that all AgentRouter 502s
are eliminated by this routing correction.

## Activation boundary

The Magpie process rule is already live. The new relay implementation requires
upgrading the installed Cladus binary; source and isolated-probe success do not
mean the active 0.1.3 service has acquired the new behavior. Service/installer
destructive acceptance tests are not run against the active user installation.

Final installer: `target/installer/cladus-0.1.4-windows-x64-setup.exe`, 7,648,651
bytes, SHA-256 `3a4cea3186b4405cde797106a6e5a3313893f0fc1a03a4a1cf35f302d6987856`.
At the final check the installed binary still reported 0.1.3, the service was
engaged without a control error, and two active relays remained. Updating the
binary requires restarting that service and interrupts its active connections.
